# NoName_project

## OpenAPI contract

- Versioned API schema is stored in `openapi/openapi.v1.json`.
- The schema is generated by `scripts/export_openapi.py`.

### Export command

```bash
make openapi-export
```

This command updates `openapi/openapi.v1.json` from the current API contract source.

### CI validation

CI runs `make openapi-check`, which:

1. Generates OpenAPI schema into a temporary file.
2. Diffs it with committed `openapi/openapi.v1.json`.
3. Fails if there is any mismatch.

This protects from situations where API changed but exported schema was not refreshed.

## API change workflow

When changing API endpoints, request/response shapes, or status codes:

1. Update API implementation and contract source (`scripts/export_openapi.py`).
2. Run `make openapi-export`.
3. Review diff in `openapi/openapi.v1.json` carefully.
4. Include schema diff in PR and explicitly call out whether the change is breaking or non-breaking.
5. Ensure CI `OpenAPI Contract` check is green.

### Contract review checklist in PR

- Are all new/changed fields documented with correct types?
- Are removed/renamed fields intentional?
- Are status code changes expected by clients?
- Is there a migration note for consumers if behavior changed?

## SemVer rules for API changes

Use semantic versioning for public API contract (`info.version` in schema):

- **PATCH** (`x.y.Z`) — backward-compatible fixes and clarifications (examples/descriptions, non-behavioral docs).
- **MINOR** (`x.Y.z`) — backward-compatible additions (new optional fields, new endpoints).
- **MAJOR** (`X.y.z`) — breaking changes (removed/renamed fields, type changes, removed endpoints, incompatible behavior).

For breaking changes:

- Bump MAJOR version in `info.version`.
- Communicate migration path in PR description and release notes.
