# MVP Spec — NoName_project

## 1. Цель
Собрать и проверить MVP веб-приложения для управления личными задачами (To-Do), чтобы пользователь мог быстро фиксировать задачи, отслеживать их статус и закрывать ежедневные дела без лишней сложности.

**Бизнес-результат первого релиза:**
- подтвердить базовую ценность продукта (создание/закрытие задач);
- получить первые количественные сигналы использования (конверсия в создание первой задачи, доля завершённых задач);
- сформировать основу для итераций (приоритеты, дедлайны, совместная работа — во 2+ релизах).

## 2. Целевая аудитория
### Primary
1. **Индивидуальные пользователи** (студенты, фрилансеры, офисные сотрудники), которым нужен простой список задач без сложных workflow.
2. **Пользователи, переходящие с заметок/мессенджеров**, которым важно быстрое добавление и понятный статус выполнения.

### Secondary
1. **Малые команды (1–5 человек)**, использующие продукт как персональный трекер (без коллаборации в MVP).

### Ключевые потребности
- быстро добавить задачу (за секунды);
- видеть список актуальных задач;
- отмечать выполнение и понимать прогресс за день.

## 3. User flow (MVP)
1. Пользователь открывает приложение и видит экран списка задач.
2. Нажимает «Добавить задачу», вводит название, сохраняет.
3. Задача появляется в списке со статусом `open`.
4. Пользователь отмечает задачу как выполненную.
5. Статус меняется на `done`, задача визуально помечается как завершённая.
6. Пользователь может удалить неактуальную задачу.

## 4. Scope In / Out
### In scope (первый релиз)
- создание задачи;
- просмотр списка задач;
- изменение статуса задачи (`open` ↔ `done`);
- удаление задачи;
- базовая клиентская валидация (пустой title запрещён);
- минимальная телеметрия продуктовых событий (create/complete/delete).

### Out of scope (не входит в MVP)
- регистрация/логин, роли и права;
- совместная работа и комментарии;
- дедлайны, приоритеты, теги, вложения;
- push/email-уведомления;
- мобильные нативные приложения;
- интеграции (календарь, Slack, etc.).

## 5. Ключевые пользовательские сценарии первого релиза

### Сценарий 1. Создание первой задачи
**Цель:** пользователь может добавить задачу и увидеть её в списке.

**Acceptance criteria (Given/When/Then):**
- **Given** пользователь находится на экране списка задач,
- **When** вводит валидный title (1–120 символов) и нажимает «Сохранить»,
- **Then** создаётся задача со статусом `open`, она отображается вверху списка, и API возвращает `201 Created`.

**Привязка к API/экранам/модулям:**
- Экран: `TaskListScreen`, модальное окно/форма `CreateTaskModal`;
- API: `POST /api/tasks`;
- Модули: `tasks-ui`, `tasks-service`, `tasks-repository`.

---

### Сценарий 2. Ошибка валидации при пустом названии
**Цель:** предотвратить создание невалидных задач.

**Acceptance criteria (чек-лист):**
- [ ] Поле title пустое и пользователь нажимает «Сохранить».
- [ ] Запрос в `POST /api/tasks` **не отправляется**.
- [ ] На форме отображается ошибка: «Введите название задачи».
- [ ] Кнопка «Сохранить» остаётся неактивной до ввода валидного текста.

**Привязка к API/экранам/модулям:**
- Экран: `CreateTaskModal`;
- API: N/A (проверка на клиенте до вызова API);
- Модули: `tasks-ui` (form validation).

---

### Сценарий 3. Отметка задачи как выполненной
**Цель:** пользователь фиксирует факт выполнения задачи.

**Acceptance criteria (Given/When/Then):**
- **Given** в списке есть задача со статусом `open`,
- **When** пользователь нажимает чекбокс «Выполнено»,
- **Then** отправляется `PATCH /api/tasks/{id}` со статусом `done`, API отвечает `200 OK`, и в UI задача отображается как завершённая (чекбокс активен, текст зачёркнут).

**Привязка к API/экранам/модулям:**
- Экран: `TaskListScreen`;
- API: `PATCH /api/tasks/{id}`;
- Модули: `tasks-ui`, `tasks-service`.

---

### Сценарий 4. Удаление неактуальной задачи
**Цель:** пользователь очищает список от лишних задач.

**Acceptance criteria (Given/When/Then):**
- **Given** в списке отображается задача,
- **When** пользователь нажимает «Удалить» и подтверждает действие,
- **Then** отправляется `DELETE /api/tasks/{id}`, API отвечает `204 No Content`, задача исчезает из списка без перезагрузки страницы.

**Привязка к API/экранам/модулям:**
- Экран: `TaskListScreen`, `DeleteTaskConfirmDialog`;
- API: `DELETE /api/tasks/{id}`;
- Модули: `tasks-ui`, `tasks-service`.

---

### Сценарий 5. Просмотр актуального списка после перезагрузки
**Цель:** пользователь видит сохранённое состояние задач.

**Acceptance criteria (чек-лист):**
- [ ] Пользователь обновляет страницу (browser refresh).
- [ ] UI выполняет `GET /api/tasks`.
- [ ] Список рендерится в течение ≤ 1 секунды при объёме до 100 задач (локальное/стендовое окружение).
- [ ] Для каждой задачи корректно отображаются title и статус (`open`/`done`).

**Привязка к API/экранам/модулям:**
- Экран: `TaskListScreen`;
- API: `GET /api/tasks`;
- Модули: `tasks-ui`, `tasks-service`, `tasks-repository`.

## 6. Минимальный набор API/экранов/модулей для верификации релиза

### API (минимум)
- `GET /api/tasks` — получить список задач;
- `POST /api/tasks` — создать задачу;
- `PATCH /api/tasks/{id}` — обновить статус задачи;
- `DELETE /api/tasks/{id}` — удалить задачу.

### Экраны
- `TaskListScreen` (основной экран списка);
- `CreateTaskModal` (создание задачи);
- `DeleteTaskConfirmDialog` (подтверждение удаления).

### Модули
- `tasks-ui` — компоненты и UX состояния;
- `tasks-service` — API-клиент и бизнес-правила;
- `tasks-repository` — доступ к хранилищу задач.

---

## 7. Definition of Done для MVP
- Реализованы все 5 сценариев выше и выполнены их критерии приемки.
- QA может воспроизвести проверки по сценариям без устных уточнений.
- API-контракты стабильны и покрывают минимальный flow создания/просмотра/завершения/удаления задач.
