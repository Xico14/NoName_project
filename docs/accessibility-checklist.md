# Accessibility Checklist

## 1) Контраст текста и интерактивных элементов

### Что проверяем
- Основной текст и вторичный текст соответствуют минимуму WCAG 2.2 AA:
  - обычный текст: **не ниже 4.5:1**;
  - крупный текст (>= 24px regular или >= 18.66px bold): **не ниже 3:1**.
- Текст и иконки внутри интерактивов (кнопки, ссылки, чипы, табы) имеют достаточный контраст.
- На сложных фонах (градиенты, glass/blur, overlay) проверяем контраст в **самой светлой и самой тёмной точке** фона.
- Состояния `hover`, `active`, `disabled`, `focus-visible` не ухудшают контраст ниже допустимого.

### Как проверяем
- Вручную через DevTools color picker/contrast.
- Автоматически через Lighthouse/axe для типовых страниц.
- Для градиентов и glass-слоёв делаем выборочную проверку минимум в 3 точках (light/mid/dark).

### Критерий готовности
- Нет текстовых и интерактивных элементов с контрастом ниже WCAG AA.

## 2) Focus ring и корректный tab-order

### Что проверяем
- Все кликабельные и фокусируемые элементы имеют видимый `:focus-visible`.
- Focus ring контрастный, не перекрывается и не обрезается контейнерами.
- Порядок фокуса следует визуальному и логическому порядку интерфейса.
- Нет “ловушек” фокуса вне модалок; в модалках фокус удерживается внутри до закрытия.
- Для кастомных контролов обеспечены `tabindex`, стрелочная навигация и ожидаемое поведение клавиш.

### Базовый паттерн
```css
:focus-visible {
  outline: 3px solid var(--focus-ring, #2563eb);
  outline-offset: 2px;
}
```

### Критерий готовности
- Любой сценарий можно пройти только клавиатурой, фокус всегда видим.

## 3) Семантика и ARIA для сложных компонентов

### Меню
- Триггер: `button[aria-haspopup="menu"][aria-expanded]`.
- Контейнер: `role="menu"`.
- Пункты: `role="menuitem"` (или `menuitemcheckbox`/`menuitemradio` при необходимости).
- Клавиатура: стрелки вверх/вниз, `Esc` закрывает меню.

### Модалки
- Контейнер: `role="dialog"` или `role="alertdialog"` + `aria-modal="true"`.
- Заголовок: `aria-labelledby`, описание: `aria-describedby`.
- При открытии фокус переносится в модалку, при закрытии возвращается на триггер.

### Табы
- Список: `role="tablist"`.
- Кнопки: `role="tab"`, `aria-selected`, `aria-controls`.
- Панели: `role="tabpanel"`, `aria-labelledby`.
- Клавиатура: стрелки перемещают фокус между табами.

### Уведомления/тосты
- Невоздушные информационные: `role="status"`, `aria-live="polite"`.
- Критичные/ошибки: `role="alert"` или `aria-live="assertive"` (осторожно, без спама).

### Критерий готовности
- Семантика читается скринридером корректно; состояния компонентов озвучиваются.

## 4) Паттерны ошибок форм

### Что обязательно
- У каждого поля есть связанный `label`.
- Ошибка и helper-текст программно связаны с полем через `aria-describedby`.
- При ошибке поле помечается `aria-invalid="true"`.
- Текст ошибки понятный и объясняет, что исправить (не только “Некорректно”).
- Ошибка визуально заметна не только цветом (иконка/текст/рамка).

### Пример
```html
<label for="email">Email</label>
<input
  id="email"
  name="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-help email-error"
/>
<p id="email-help">Используйте рабочий адрес в формате name@company.com.</p>
<p id="email-error" role="alert">Введите корректный email, например name@company.com.</p>
```

### Критерий готовности
- Ошибки понятны визуально и скринридеру, связь поле↔сообщение не теряется.

## 5) Процесс: обязательные accessibility-проверки

Перед merge проверяем:
- [ ] Контраст текста и интерактивов (включая градиенты и glass-слои).
- [ ] Видимый focus ring у всех интерактивов.
- [ ] Полная keyboard-навигация и корректный tab-order.
- [ ] ARIA/семантика для меню, модалок, табов, уведомлений.
- [ ] Формы: корректная связка label/help/error, `aria-invalid`, понятные тексты ошибок.
- [ ] Нет критичных accessibility-ошибок в Lighthouse/axe на основных сценариях.
